# 0.2.0 upgrade and iPhone checks

Version 0.2.0 requires protocol v2 on both the local MCP agent and the phone app. Old pairings cannot approve requests after upgrading. Finish or cancel pending requests before restarting the agent.

## Upgrade

1. In your MCP client, keep `command` as `npx` and set its arguments to `["-y", "@askahuman/mcp@0.2.0", "serve"]`, preserving any existing relay/name flags. Restart that MCP server. To check the downloaded release separately, run:

   ```sh
   npx -y @askahuman/mcp@0.2.0 version --json
   ```

2. Open the phone app online, close it, and reopen it so the service-worker update can take effect. In **Add agent**, check that the footer shows `0.2.0` and the same short commit as the command above. Do not test until both match. Self-hosters must deploy their matching web and relay builds first.
3. Call `start_pairing` with `{"reset":true}` in each updated MCP agent. Enter the fresh code shown in its local terminal or pairing page. A code never belongs in chat or a shared screenshot. Remove obsolete phone entries after the replacement works.
4. Open the installed Home Screen app and tap **Enable notifications** if needed. Confirm it reports notification setup for every paired agent. iPhone Web Push requires iOS 16.4 or later, an installed Home Screen web app, and permission requested by a user gesture. See [WebKit's platform guidance](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

The phone requires working WebCrypto and IndexedDB. Missing signing or sequence storage shows repair guidance and requires re-pairing. A relay interruption can reconnect with the same pairing; restarting the local MCP process loses its pairing keys. An answer receipt confirms that the agent accepted an answer; it does not confirm execution of another operation.

## Physical iPhone acceptance

Use synthetic questions only. Record the iOS version, app version/commit, failing step, and observed behavior; exclude pairing codes and push subscription URLs from shared evidence.

| Check | Expected result |
| --- | --- |
| Full question and canceled swipe | Read the final title/body markers. Begin an approval swipe, then cancel vertically. The question remains unanswered; Decline returns exactly `approved:false`. |
| Choices and keyboard | Reach option 32 and read its full label. Enter `😀é漢字🚀` in a five-character text field; the counter is 5/5 and the returned text matches exactly. Controls remain reachable with the keyboard open. |
| Receipt and long reply | After acceptance, the verified receipt label remains visible. A long reply is fully scrollable, the receipt stays until Done or another request, and Done returns to listening. |
| Expiry and reconnect | Background a 15-second request for at least 20 seconds. Its deadline does not reset and it cannot approve. For a separate request, toggle Airplane Mode for about 10 seconds, reconnect, then decline the same question. |
| Two agents and locked phone | Pair A and B with notifications enabled. Close/reopen the app, lock the phone, and request A, B, then A. Each generic notification opens the correct agent. Forget A; B still receives notifications. |
| Permission state | Block notifications in iPhone Settings and reopen the app. The blocked state is visible. Restore permission and remove synthetic test pairings when finished. |

A guided terminal driver creates two isolated MCP processes, checks their exact released version/commit, sends these harmless questions, and verifies their MCP results:

```sh
node scripts/iphone_acceptance.mjs /absolute/path/to/ask-a-human 0.2.0 FULL_40_CHARACTER_COMMIT
```

Use the published binary or the binary installed inside the npm package's `bin` directory. The driver prints pairing information only to your local terminal/loopback page. It never connects an answer to a deployment, purchase, deletion, or other external action. Notification delivery and visual checks require your observations; browser automation does not certify a physical iPhone.
